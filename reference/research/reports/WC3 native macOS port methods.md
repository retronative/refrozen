# Recompile Frozen Throne, don't reimplement it

The best fit for reFrozen is a static recompile of all three 1.26a binaries (war3.exe, Game.dll and Storm.dll, plus probably Mss32.dll), built on **JTM-rootstorm/x86recomp**. It is the only open-source tool that lifts 32-bit Win32 PE files to portable C++. It is MIT-licensed, treats macOS on Apple Silicon with Metal as a hard requirement, lifts several DLLs in one run, and models x87 math exactly. It is also very new: about one week of public history, 2 stars, one author, and no game it claims as fully playable. The general-purpose lifters do not fill the gap either. McSema and llvm-mctoll are archived, Rellume has no x86-32 support, RetDec is a decompiler in limited maintenance, and remill gives you instruction semantics but no Win32 front end. The other two routes miss the goal in different ways. Wine still runs 32-bit WC3 on Apple Silicon only through Rosetta 2, which Apple cuts back to a gaming subset in macOS 28, until CrossOver 27 moves to native arm64 Wine plus FEX. The open-source engines (OpenWar3, OpenRealm, Warsmash) cannot yet play DotA 6.83 on 1.26a data, and none of them tries to stay in lockstep with real 1.26a clients. Only a recompile of the original code can keep **bit-exact lockstep** with Windows players, since W3GS sends only player actions. Even so, nobody has publicly shown a large 32-bit Win32 game fully playable on arm64 macOS through static recompilation, so this is frontier work. The deciding M0 fact, Game.dll's import table, is still unknown, because the local patch contains only binary deltas.

## Only one x86 recompiler is built for this job

Static recompilation of x86-32 Windows code took off in 2026. **x86recomp** describes itself as "Static recompilation of 32-bit x86 Windows games into native 64-bit programs" with "no emulator, interpreter or Wine in the result" ([x86recomp](https://github.com/JTM-rootstorm/x86recomp)). Its lifter decodes a PE with Zydis and emits one C++ function per guest function, "with exact x86 integer and flag semantics". DLLs are lifted in the same pass with `--module game.dll`, which matches WC3's exe + Game.dll + Storm.dll layout. The runtime provides a 4 GiB guest arena, PE loading, threads, SEH, and HLE for kernel32/user32/gdi32/advapi32, Miles, Bink, DirectSound 8, DirectInput 8, DirectDraw7/D3D7, OpenGL 1.x and D3D9 (in progress), all rendered through SDL_GPU, "native Metal on macOS" ([x86recomp](https://github.com/JTM-rootstorm/x86recomp)). Its architecture document makes Apple Silicon a hard constraint: nothing may assume an x86 host or 4 KiB pages, and "an indirect branch to an address that was not lifted is a fatal error" ([ARCHITECTURE.md](https://github.com/JTM-rootstorm/x86recomp/blob/main/ARCHITECTURE.md)). The author's reasoning applies directly to WC3, an MSVC 2005 binary: "Early-2000s MSVC code is integer + x87, ~190 mnemonics, few SEH frames, so a purpose-built lifter is tractable." Function lists and jump tables come from a Ghidra export plus a per-game manifest ([ARCHITECTURE.md](https://github.com/JTM-rootstorm/x86recomp/blob/main/ARCHITECTURE.md)).

Two gaps matter for WC3. First, Direct3D 8 is not in its HLE list, although WC3's `-opengl` renderer could use the existing OpenGL 1.x path. Second, Winsock is not listed. The bigger risk is maturity. The tool has **80 commits between 2026-10-12 and 2026-10-19**. Its own projects are Dungeon Siege (where it was developed), Call of Duty "in progress" and LEGO Star Wars "started", and its README makes no playability claim ([GitHub API](https://api.github.com/repos/JTM-rootstorm/x86recomp); [DS1-Rebuilt](https://github.com/JTM-rootstorm/DS1-Rebuilt)).

The other two x86 recompilers show what lies ahead. **sp00nznet/xboxrecomp** (MIT, with LGPL parts from xemu; 937 commits, 287 stars, macOS arm64 host) has lifted 22,097 functions for Burnout 3. Even so, it "retired" its earlier claim that Burnout 3 was playable, and its README calls indirect calls "the hardest 10%" ([xboxrecomp](https://github.com/sp00nznet/xboxrecomp)). Its changelog lists the x87 bugs that broke games: FIST ignored the rounding mode, fxch was a no-op, and 904 instructions were initially emitted as comments. It also records that on arm64 macOS "every fixed base sits inside `__PAGEZERO`", and that `MAP_FIXED` silently replaced live mappings ([xboxrecomp](https://github.com/sp00nznet/xboxrecomp)). **M-HT/SR** (MIT/GPLv2+/LGPLv2.1+, 426 stars, last commit 2026-08-27) has a longer track record. It has shipped Septerra Core and Battle Isle 3 (Win32) and Warcraft: Orcs & Humans (DOS) to macOS arm64, by going through assembly and an LLVM IR step with hand-written per-game annotations ([M-HT/SR](https://github.com/M-HT/SR)). That design works for small titles but is a poor match for a 12 MB Game.dll. Nobody has found a WC3 recompile project, and no public source gives Game.dll's function count or how often it uses indirect calls.

Research systems such as Lasagne, which proves its x86-to-Arm memory-model mappings and cuts fences by 45.5% on average ([PLDI'22](https://pldi22.sigplan.org/details/pldi-2022-pldi/52/Lasagne-A-Static-Binary-Translator-for-Weak-Memory-Model-Architectures)), and a 2026 superset-CFG paper ([arXiv 2609.16423](https://arxiv.org/abs/2609.16423)) are useful for ideas but target x86-64 Linux. x86recomp's exact x87 model matters more for WC3 than for most games. It runs on Berkeley SoftFloat with "precision and rounding control, status-word flags", "tested bit for bit against a real x87" ([x86recomp](https://github.com/JTM-rootstorm/x86recomp)). That is the property online play depends on.

## Wine works today, but only while Rosetta lasts

Every stable Wine distribution for Apple Silicon is still **x86-64 Wine under Rosetta 2**. WC3's 32-bit code runs inside it through WoW64 ([The Register](https://www.theregister.com/software/2026/01/15/wine-11-runs-windows-apps-in-linux-macos-better-than-ever/5087238)). Rosetta cannot run standalone 32-bit x86 apps ([Apple Community](https://discussions.apple.com/thread/253527701)). Apple has said that from macOS 28 only "a subset" of Rosetta will remain, for older games ([MacRumors](https://www.macrumors.com/2025/06/10/apple-to-phase-out-rosetta-2/)). OSNews goes further and calls macOS 27 the last release with Rosetta at all ([OSNews](https://www.osnews.com/story/145279/macos-27-drops-intel-support-will-be-last-release-with-rosetta-2/)). The two accounts conflict, and the scope of Apple's subset is still unclear. CodeWeavers' answer is a July 2026 CrossOver Preview with native arm64 Wine and a custom macOS FEX ([CodeWeavers blog](https://www.codeweavers.com/blog/mjohnson/2026/7/31/crossover-preview-the-right-to-bear-arm64-on-mac); full post not read, 403). CrossOver 27, expected early 2027, reportedly drops 32-bit bottles but runs "almost all 32-bit applications" in 64-bit ones ([machow2](https://machow2.com/run-32-bit-apps-mac/)). CrossOver itself is proprietary, though its Wine changes are LGPL. Upstream native aarch64 Wine on macOS still fails with a "Malformed Mach-O" loader ([Wine Bug 58567](https://list.winehq.org/hyperkitty/list/wine-bugs@list.winehq.org/thread/AIEGB45LZWRUP7UAVUWQPPRXFVZU5I7L/)). Whisky was archived in May 2025 ([Whisky](https://github.com/Whisky-App/whisky)). Hangover, Box64 and upstream FEX all target arm64 *Linux* ([Hangover](https://github.com/AndreRH/hangover/releases)).

Graphics shows why Apple's own stack does not help. WC3 asks for "DirectX 8.1 or newer" (a 2003 report, [Wine Bug 1211](https://list.winehq.org/pipermail/wine-bugs/2003-June/005641.html)) and switches to OpenGL with `-opengl` ([CodeWeavers tip](https://codeweavers.com/compatibility/crossover/tips/warcraft-iii-reign-of-chaos/use-opengl-instead-of-direct3d)). The evidence that 1.26a specifically uses D3D8 is indirect, and it will be confirmed only once Game.dll's import table is read. **D3DMetal handles only 64-bit DX11/12, and DXMT only D3D10/11** ([highball PR](https://github.com/gauthierpiarrette/highball/pull/142); [DXMT #4](https://github.com/3Shain/dxmt/discussions/4)). That leaves wined3d, DXVK's d3d8 support (since v2.4) on MoltenVK ([DXVK](https://en.wikipedia.org/wiki/DXVK)), d3d8to9 (BSD-2) ([d3d8to9 fork](https://github.com/Fanatic-64/d3d8to9)), and experimental D3D9-to-Metal drivers such as mtld3d, which lists D3D8 as planned ([mtld3d](https://github.com/trozzelle/mtld3d)), and d9mt ([d9mt](https://github.com/jdrly/d9mt)). A CodeWeavers user guide recommends the "D3DMetal" setting for WC3 1.26a ([CodeWeavers forum](https://www.codeweavers.com/compatibility/crossover/forum/warcraft-iii-patch-126a?msg=332996)). That conflicts with D3DMetal's DX11/12-only scope. Most likely the setting silently falls back to wined3d.

Real-world reports are mixed. A prebuilt Apple Silicon bottle crashes when you click Options, and Battle.net does not work ([Johnny Matthews](https://johnnymatthews.dev/blog/2025-08-06-install-the-original-warcraft-3-on-apple-silicon/)). A 2021 M1 user reported DotA at 9–20 FPS ([MacRumors](https://forums.macrumors.com/threads/warcraft-iii-tft-1-26a-on-macbook-pro-m1.2283317/)). The iCCup anti-hack launcher has a history of failing under Wine ([WineHQ bug 23873](https://www.winehq.org/pipermail/wine-bugs/2011-May/275877.html)).

Wine is more useful to reFrozen as **LGPL-2.1 reference code** (ws2_32, dsound, d3d8 in wined3d) than as a runtime. Classic Winelib is legacy, since every module has built as PE since Wine 8 ([Wine 8.0 notes](https://admin-magazine.com/News/Wine-8.0-Released)). Dynamically linking unmodified or published Wine libraries is allowed, but modified Wine source must be released ([BetaNews](https://betanews.com/article/does-a-leading-windows-environment-for-mac-violate-the-lgpl/)).

## Reimplementations play DotA partially, but never in lockstep

Three engines are actively working on DotA, and **none plays 6.83 on 1.26a data**. **OpenWar3** (TypeScript, MIT, created 2026-07) has gone furthest. Its creep waves walk all three lanes and Drow's five skills can be learned, but on DotA **6.77b AI** ([openwar3 #224](https://github.com/elevchyt/openwar3/issues/224)). It also refuses any install other than TFT **1.30.4**, which rules out a 1.26a project unless you fork it ([README](https://github.com/elevchyt/openwar3)). **OpenRealm/openwarcraft3** (C, SDL2, MIT, 355 stars, last commit 2026-10-23) reads the player's own War3.mpq/War3x.mpq and builds on macOS. Its own documentation says it "cannot yet *play*" DotA 6.83d: it parses the 4.1 MiB script and enters `main()`, but custom abilities and HUD drawing are unfinished ([dota-map-playability.md](https://github.com/corepunch/open-realm/blob/main/docs/games/warcraft-3/dota-map-playability.md)). **Warsmash** (Java/LibGDX, AGPL-3.0, 585 stars) supports 1.22–1.28 MPQs and has its own ANTLR-based JASS VM. Nothing shows it playing DotA ([Warsmash](https://github.com/Retera/WarsmashModEngine)).

All three engines show how long the tail is. OpenWar3 counted 136 missing natives across 5,019 call sites. It also found that a stubbed `IsUnitVisible` returning FALSE inverted all 153 of DotA's targeting checks ([map-compatibility.md](https://github.com/elevchyt/openwar3/blob/main/docs/map-compatibility.md)). OpenRealm counted 525 natives in DotA's script, 137 of them unregistered at first, and a `SetPlayerAbilityAvailable` stub with 650 references ([dota-map-playability.md](https://github.com/corepunch/open-realm/blob/main/docs/games/warcraft-3/dota-map-playability.md)).

The real disqualifier is the networking design, not maturity. OpenWar3 says determinism is "not required for sync — only one machine simulates" ([multiplayer.md](https://github.com/elevchyt/openwar3/blob/main/docs/multiplayer.md)). OpenRealm uses Quake-style server-authoritative snapshots ([ARCHITECTURE.md](https://github.com/corepunch/open-realm/blob/main/ARCHITECTURE.md)), and Warsmash relays orders through its own server. W3GS, by contrast, carries only player actions ([BNETDocs 0x48](https://bnetdocs.org/packet/468/w3gs-incoming-action2)). A reimplementation therefore can never join a game hosted by a real 1.26a client. Warsmash issue #99, where kill credit changed because of the order units update within a tick, shows how small a divergence it takes ([Warsmash #99](https://github.com/Retera/WarsmashModEngine/issues/99)).

The libraries, in contrast, are mature and mostly permissive. **StormLib** (MPQ, MIT, pushed 2026-10-12) and **CascLib** (MIT) are maintained by Ladislav Zezula ([StormLib](https://github.com/ladislav-zezula/StormLib); [CascLib](https://github.com/ladislav-zezula/CascLib)). **War3Net** (C#, MIT) and **wc3libs** (Java, Apache-2.0) cover the W3X sub-formats ([War3Net](https://github.com/Drake53/War3Net); [wc3libs](https://github.com/inwc3/wc3libs)). There are MIT BLP readers (WarRaft/blp-lib) and MIT MDX parsers (mdx-m3-viewer, Retera Model Studio). On the JASS side, **pjass** (BSD-2) checks syntax and **jassdoc** documents native semantics ([pjass](https://github.com/lep/pjass); [jassdoc](https://github.com/lep/jassdoc)). There is no standalone embeddable JASS VM. The working ones live inside the engines, and OpenRealm's C VM is the easiest to lift out. For a recompile these are test oracles, not replacements. DotA's protected MPQ uses `wSectorSizeShift=15` (16 MiB sectors), a fake `(listfile)` and a truncated w3i ([OpenRealm doc](https://github.com/corepunch/open-realm/blob/main/docs/games/warcraft-3/dota-map-playability.md); [openwar3 docs](https://github.com/elevchyt/openwar3/blob/main/docs/map-compatibility.md)), so StormLib is the right reference for checking how lifted Storm code handles those maps.

## 1.26a is unpacked MSVC 2005 code with ordinal-only Storm exports

Local header parsing of the official patch shows that **1.26a's binaries are BSDIFF40 deltas** inside `Patch_War3x.mpq`. The delta headers give target sizes of Game.dll 12,042,240 bytes, War3.exe 471,040 bytes and Storm.dll 339,968 bytes, all built on 2011-03-18. The iCCup-shipped Storm.dll matches stock 1.26a exactly (local analysis of `../DOTA/ICC Game client install/War3TFT_126a_English.exe` and `../DOTA/iCCup_Launcher/app/Launcher/Storm.dll`). Storm.dll was built with VS2005 (build 50727) against MSVCR80, uses C++ exception handling and is not packed. It has **814 export slots, of which only 53 are named**. The classic `SFile*/SMem*/SStr*/SNet*` C API is exported by ordinal only, and Storm.dll has no Winsock import (local analysis). The ordinal-only exports would be a serious problem for anyone reimplementing Storm, because StormLib gives MPQ behaviour but not Storm's binary interface. **Under x86recomp the problem goes away**: Storm.dll is lifted alongside Game.dll, so the ordinals resolve inside the lifted image.

The 1.26 release is version 1.26.0.6401, from 2011-03-24 ([Liquipedia](https://liquipedia.net/warcraft/Patch_1.26)). The iCCup kit also includes a UPX-packed `d3d8.dll` proxy that exports `Direct3DCreate8`, which strongly suggests Game.dll uses D3D8 directly (local analysis). WarcraftHelper recommends d3d8to9 for 1.20e and 1.24e ([WarcraftHelper](https://github.com/LoveBeforT/WarcraftHelper)). iCCup ships `FPSUnlocker.mix` (local file), and RenderEdge Widescreen is also distributed as a `.mix` ([Lutris installer](https://lutris.net/games/install/38682/view)). Both fit WC3's known loading of `.mix` plugins from its folder, a standard way to inject DLLs.

There is no legal public decompilation. Per-version Game.dll offsets live in hook projects:

Any port that wants to reach PvPGN servers has to reproduce that logon-proof replacement. Warden is server-delivered Battle.net anti-cheat ([Wowpedia](https://wowpedia.fandom.com/wiki/Warden_(software))), not code in the shipped binaries. On the network side, W3GS and the Battle.net protocol are documented on BNETDocs ([BNETDocs](https://bnetdocs.org/document/16)), with PvPGN as the GPL-2.0 reference server ([pvpgn-server](https://github.com/pvpgn/pvpgn-server)).

The original Mac client is a weaker recompile input than it looks. It was Universal from patch 1.21 ([Macworld](https://www.macworld.com/article/183256/war3-2.html)) and used Open Transport ([Hive snippet](https://www.hiveworkshop.com/threads/warcraft-iii-on-wineskin-mac.257050)). Nobody has checked whether its symbols survive, and none is on this machine.

The legal exposure is real. The WC3 EULA §3A bans reverse engineering, decompiling and derivative works, and §3C(iv) bans emulating Battle.net protocols ([EULA copy](https://data.gpo.zugaina.org/src_prepare-overlay/licenses/Warcraft3_EULA)). *Davidson & Associates v. Jung* (8th Cir. 2005) held those clauses enforceable against the bnetd developers ([opinion](https://ecf.ca8.uscourts.gov/opndir/05/09/043654P.pdf)). Accounts of Warsmash conflict: 80.lv reported a 2022 Blizzard demand to stop, after which the repo vanished ([80.lv](https://80.lv/articles/blizzard-demanded-to-stop-the-development-of-the-warsmash-engine/)), while Warsmash's current README says the rumoured cease-and-desist "did not happen" ([Warsmash](https://github.com/Retera/WarsmashModEngine)). Long-lived projects such as StormLib, PvPGN and UjAPI do not redistribute Blizzard code. ReCarbon's model, in which only the tooling is published and the recompile is generated locally from the player's own copy, is the lowest-exposure form these sources point to. Still, it does not cancel the EULA's reverse-engineering ban. The leaked 1.x source and the Reforged 2.0.1 debug symbols ([Hive](https://hiveworkshop.com/threads/blizzard-accidentally-releases-debug-symbols-maps-and-exclusive-content-in-warcraft-3-update-version-2-0-1.357413)) must never be inputs.

## Recommended approach: fork x86recomp, lift everything, add D3D8 and Winsock

Vendor or fork x86recomp (MIT) as reFrozen's toolchain, in the same role SpeedBreaker played for ReCarbon. First, apply the patch locally to bring a 1.21b install to 1.26a. Then export function lists and jump tables from Ghidra for war3.exe, Game.dll, Storm.dll and Mss32.dll, and lift all four in one run. Keep Storm.dll lifted rather than reimplemented, and use StormLib as the oracle for protected-map behaviour.

For graphics, try WC3's `-opengl` renderer on x86recomp's OpenGL 1.x HLE before writing a D3D8-to-Metal layer. Use mtld3d and wined3d's d3d8 as references for the D3D8 layer if it turns out to be needed. Write Winsock HLE onto BSD sockets, with Wine's ws2_32 as reference. Choose between using x86recomp's Miles HLE and lifting Mss32.dll once the imports are known.

Keep x86recomp's exact x87 and SSE models, and do not replace them with native floats. Bit-exact lockstep depends on them, and so does replay compatibility. Check this at M6 against a Windows 1.26a peer over LAN.

Expect the long tail xboxrecomp hit: vtable and JASS-native indirect calls, x87 edge cases, `lock`-prefixed atomics and memory placement around `__PAGEZERO`. Keep CrossOver 26 as a gameplay oracle while Rosetta lasts. Treat OpenRealm and OpenWar3 as sources of DotA test cases and native-semantics notes, not as code paths.

Do this only after M0 shows two things: Game.dll is unpacked and does not modify its own code, and its imports fit an HLE surface of reasonable size. If x86recomp proves unworkable, the fallback is remill semantics on a Ghidra CFG with a runtime written for reFrozen, which costs more for the same result. A reimplementation is the wrong fallback for this goal.

- **UNRESOLVED**: The licence of the w3l loader. The threading model. Whether the 1.26a Mac build keeps its symbols.

## Conclusion

The research turns the question around. The hard part is not getting WC3 to *run* natively; Wine already does that and a reimplementation could eventually do it. The hard part is keeping **1.26a's exact simulation**, because DotA's value is in online games with existing Windows players, and W3GS lockstep tolerates no drift. That requirement rules out every reimplementation. It also makes the most important feature of the chosen recompiler its bit-exact x87 model, more than its speed or how much of the API it covers. Storm.dll's ordinal-only exports, which look like a reason to reimplement it, are instead a reason to lift it.

The timing is good but unproven. x86recomp appeared in October 2026, and Rosetta's retreat in 2027 gives a native port a real reason to exist. But reFrozen would likely be the largest Win32 title any public x86 recompiler has tried. M0 should treat x86recomp as a hypothesis to falsify quickly: patch to 1.26a, read Game.dll's imports, and lift Storm.dll first as a small test.
